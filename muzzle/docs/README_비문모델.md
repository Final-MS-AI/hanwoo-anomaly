# 비문 개체식별 모델 — 인계 문서

---

## 1. 세 줄 요약

1. 소의 코 사진을 **512차원 숫자 벡터**로 바꾸는 모델을 만들었다.
2. 같은 소끼리는 벡터가 가깝고 다른 소끼리는 멀다. **거리만 재면 누구인지 알 수 있다.**
3. 새 소를 등록해도 **재학습이 필요 없다.** 사진 3장 찍어 벡터를 DB에 넣으면 끝.

---

## 2. 왜 분류기가 아닌가

처음 떠오르는 방법은 "268마리 중 누구인지 맞히는 분류기"다. **제품에는 못 쓴다.**
농가가 소를 등록할 때마다 클래스가 늘고 그때마다 모델을 다시 학습해야 하기 때문이다.

|              | 분류기               | 채택한 임베딩 방식         |
| ------------ | -------------------- | -------------------------- |
| 새 개체 등록 | 재학습 필요          | **사진 3장 → DB 저장. 끝** |
| 출력         | "3번 소"             | 512차원 벡터               |
| 판정         | argmax (무조건 답함) | 코사인 유사도 + 임계값     |
| 확신 없을 때 | 억지로 답함          | **"미확정" 보류 가능**     |

마지막 줄이 핵심이다. 기획서 §2의 **"저신뢰도는 강제 부여하지 않고 미확정 보류"** 설계가
이 구조에서만 구현된다. 소 A의 행동이 소 B 이력에 기록되면 두 개체 baseline이 동시에 오염되므로,
개체 식별만은 "놓치는 것"보다 **"잘못 붙이는 것"이 더 나쁘다.**

---

## 3. 만든 방법

- **데이터**: Zenodo 6324361 — 268두 / 4,923장 (Angus 등, CC BY 4.0)
- **모델**: EfficientNet-B0 + **ArcFace** (YOLO 아님. YOLO는 "어디 있냐", 이건 "누구냐")
- **전처리**: 그레이스케일 + CLAHE
  비문 정보는 색이 아니라 **코 표면 융기 무늬(texture)** 다. 데이터셋에 Angus(검은 코)와
  Hereford 교잡(밝은 코)이 섞여 있어 컬러 학습 시 모델이 **코 피부색**을 지름길로 배울 수 있다.
- **증강**: 축소→확대 + JPEG 재압축(저화질 시뮬), 회전, 랜덤크롭. **좌우반전 금지**(비문은 좌우 비대칭)
- **분할**: 268두를 **마리 단위로** 201 학습 / 67 평가
  이미지 단위 랜덤 분할은 같은 소가 양쪽에 들어가 정확도를 부풀린다

## 4. 성능

각 소를 사진 3장으로 등록하고 나머지로 조회하는 **실제 운영 절차 그대로** 측정했다.

### 4-1. 미학습 개체 (학습에서 한 번도 안 본 67두)

| 지표                | 값         | 기획서 §9 목표 | 판정 |
| ------------------- | ---------- | -------------- | ---- |
| Top-1 정확도        | **0.9921** | ≥ 0.90         | 충족 |
| 오배정률 @0.40      | **0.0059** | ≤ 0.02         | 충족 |
| 미확정 보류율 @0.40 | 0.0138     | (보조)         | —    |

### 4-2. 교차 데이터셋 (Cows Frontal Face — 파키스탄 / 다른 품종 / 스마트폰)

**재학습 없이 등록만 하고** 측정했다. 국가·품종·카메라가 전부 다르다.

| 지표                | 값         | 비고                      |
| ------------------- | ---------- | ------------------------- |
| 코 검출률           | **0.9925** | YOLO-World zero-shot      |
| Top-1 정확도 (67두) | **0.8127** | 무작위 추측은 0.0149      |
| 오배정률 @0.40      | 0.1873     | in-domain 대비 **31.7배** |
| 미확정 보류율 @0.40 | **0.0000** | ← 아래 §5 참고            |

**해석**: 국가·품종·카메라가 모두 바뀌었는데 재학습 없이 Top-1 81.3%가 나왔다.
비문 융기 패턴이 품종이 아닌 **종 수준 형질**이라는 가설을 지지하는 정량 근거다.

## 5. ★ 가장 중요한 발견 — 임계값은 도메인을 넘지 못한다

교차 데이터셋에서 **보류율이 0.0000이다.** 임계값 0.40에서 단 한 건도 보류되지 않았다.
전부 ID를 부여했고, 그중 18.7%가 틀렸다.

즉 모델은 **틀릴 때도 자신 있게 틀린다.** 도메인이 바뀌면 임베딩이 좁은 영역으로 몰려
서로 다른 개체 간 유사도까지 높아지고, 그 결과 **거부 장치가 작동하지 않는다.**

|          | in-domain | 교차 도메인 | 변화               |
| -------- | --------- | ----------- | ------------------ |
| 오배정률 | 0.0059    | 0.1873      | **31.7배 악화**    |
| 보류율   | 0.0138    | 0.0000      | **거부 기능 소실** |

### 이것이 실무에 주는 지시

**임계값 0.40은 in-domain에서만 검증된 값이다.**
한우 등 새 도메인에 배포할 때는 **그 도메인 데이터로 임계값을 재보정해야 한다.**
등록 초기 운영 절차에 **임계값 캘리브레이션 단계를 반드시 포함할 것.**

이건 실패가 아니라 **설계 요구사항이 하나 도출된 것**이다.

### 5-1. 실촬영 영상에서 재확인 (2026-08-06)

인터넷 공개 영상(등록 5두 / 조회 30건 / 미등록 30건)으로 세 번째 도메인을 측정했다.

|               | Zenodo (in-domain) | Cows Frontal Face | **실촬영 영상**  |
| ------------- | ------------------ | ----------------- | ---------------- |
| 오배정률      | 0.0059 @0.40       | 0.1873 @0.40      | **0.3333 @0.45** |
| 보류율        | 0.0138             | 0.0000            | 0.0333           |
| 미등록 오확정 | 0.0000 @0.45       | —                 | **0.6667 @0.45** |

**§5의 결론이 실촬영 도메인에서 그대로 재현됐다.** 다만 이번에는 처방까지 나왔다 —
동일 도메인에서 **임계값 0.70이 오배정률 0.0000**을 달성한다.

즉 임계값 캘리브레이션은 "있으면 좋은 것"이 아니라 **배포 필수 절차**임이
두 개의 독립적인 도메인에서 확인되었다.

#### ★ 열화 조건에서도 원칙이 지켜진다

임계값 0.70 고정, 해상도를 낮춰가며 측정:

| 배율  | Top-1  | 확정률 | 오배정률   | 보류율 |
| ----- | ------ | ------ | ---------- | ------ |
| 1.000 | 0.6333 | 0.3333 | **0.0000** | 0.6667 |
| 0.500 | 0.6000 | 0.3333 | **0.0000** | 0.6667 |
| 0.250 | 0.4667 | 0.2000 | **0.0000** | 0.8000 |
| 0.125 | 0.3000 | 0.2000 | **0.0000** | 0.8000 |

**해상도가 1/8이 되어도 오배정은 0건이다.** 잃는 것은 확정률이고, 그만큼 보류가
늘어난다. 화질이 나빠지면 모델은 **틀리는 것이 아니라 "모르겠다"고 말한다.**

§2에서 "개체 식별만은 놓치는 것보다 잘못 붙이는 것이 더 나쁘다"고 설계한 원칙이,
설계 의도대로 열화 조건에서 작동함을 보인 결과다.

반대로 임계값 0.45에서는 같은 열화 조건에서 오배정률이 0.33~0.37로 유지된다.
**오배정을 결정하는 것은 화질이 아니라 임계값이다.**

> 2026-08-07 재실행에서 위 표와 동일한 수치가 나왔다. 재현성이 확인된 결과다.

Top-1(임계값 무관)의 붕괴 지점은 **0.25배**다. 1/2까지는 0.6333 → 0.6000으로
거의 유지된다. "기존 CCTV로 가능하다"는 주장의 정량적 하한이다.

**주의**: 등록 5두라 무작위 추측이 0.200이다. 이 표의 절대 수치를 §4의 67두 결과와
직접 비교하면 안 되며, 도메인 간 _경향_ 비교로만 읽어야 한다.

## 6. 한계

- **한우 자체 검증 미수행.** 공개 한우 비문 데이터셋이 존재하지 않고, 선행 한우 연구
  데이터는 비공개이며, 농가 촬영도 불가능했다. **명시적 한계이자 1순위 후속 과제.**
- 전용 코 검출기는 학습하지 못했다. Cows Frontal Face 공개 레코드에 바운딩박스 주석이
  포함되어 있지 않다. 대신 **YOLO-World zero-shot으로 검출률 0.9925**를 확인했다.
- 등록 경로는 앱의 **가이드 오버레이**로 구도가 고정되므로 전용 검출기 없이
  중앙 크롭으로 대체 가능하다.
- **실촬영 영상에서 자동 코 검출 불가.** YOLO-World zero-shot은 정면 근접 정지
  사진에서만 동작한다(Cows Frontal Face 검출률 0.9925). 소가 움직이고 거리·각도가
  변하는 실영상에서는 **검출률 0%** 였다. 평가는 수동 ROI + 템플릿 추적으로
  대체했으며, **전용 코 검출기 학습이 1순위 후속 과제**다.

## 7. 백엔드 연동

### 입력 전제

이 모델은 **코 부위만 잘린 크롭 이미지**를 받는다.
원본에서 코를 찾아 자르는 것은 이 모듈의 역할이 아니다.

### 등록

```python
from muzzle_encoder import MuzzleEncoder
enc = MuzzleEncoder("muzzle_encoder.pt")

vec = enc.enroll([crop1, crop2, crop3])   # (512,) float32 → DB 저장
```

### 조회

```python
gallery = {개체번호: 등록벡터}
cow_id, score = enc.identify(crop, gallery)

if cow_id is None:
    상태 = "미확정"   # ID 부여하지 않는다. 시계열에 기록하지 않는다.
```

### 지켜야 할 것

1. **임계값은 경로마다 다르다 — `muzzle/THRESHOLD_POLICY.md`가 정본이다.**
   - `/muzzle/identify` 기본값 **0.70** (실촬영 CCTV 도메인, `video_openset.csv` 근거)
   - in-domain 정지 사진 0.45 (2026-07-31 미등록 22두 실측으로 0.40에서 상향.
     미등록 개체 최고 유사도 0.4265, 0.43 이상에서 전량 차단)
   - 변경하려면 해당 도메인의 open-set 곡선을 근거로 제시할 것.
     정책 문서 §7의 변경 조건을 따른다
2. **전처리를 임의로 고치지 마라** — 그레이스케일·CLAHE·224 리사이즈가 학습과 어긋나면
   정확도가 통째로 날아간다. `muzzle_encoder.py`의 `_preprocess()`를 그대로 쓸 것.
   **이런 종류의 버그는 8월 말 통합 시점에 터진다.**
3. **등록은 3장 이상** — 1장이면 성능이 떨어진다
4. **"미확정"은 에러가 아니라 정상 동작** — 재시도 유도하지 말고 다음 방문을 기다린다
5. **DB 스키마**: `embedding float[512]` 컬럼 필요 (PostgreSQL 배열 또는 pgvector)
6. **여러 장 등록 시 동일 개체인지 검사한다** — API가 쌍별 코사인 유사도 최솟값을
   확인하고, 0.45 미만이면 HTTP 422로 거부한다. 검사 이전에는 서로 다른 소 3장이
   평균되어 "아무 개체도 아닌 벡터"가 조용히 저장됐다. 1장 등록 시에는 검사하지 않는다.
   이 값은 식별 임계값과 별개로 관리한다 — 목적이 다르다.
7. **원본에서 코를 자동으로 찾는 수단은 아직 없다** — 실촬영 영상 검출률 0%.
   등록은 앱 가이드 오버레이로, 평가는 수동 ROI로 해결하고 있다.
8. **임계값은 도메인마다 다시 정한다** — in-domain 0.45, 실촬영 영상 0.70.
   새 환경에 배포할 때는 그 환경 데이터로 캘리브레이션할 것.
   **절차는 `muzzle/THRESHOLD_POLICY.md` §6에 단계별로 정리되어 있다.**
   이 절차 없이 배포하면 임계값이 무의미하다.
