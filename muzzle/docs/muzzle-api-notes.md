## 0. 세 줄 요약

- 비문 모델을 **별도 FastAPI 서비스(포트 8001)** 로 감쌌다. 팀원 백엔드(8000)와 분리했다.

## 1. 왜 API가 필요했나

앞선 작업에서 DB 테이블 3개(`cattle`, `muzzle.enrollment`, `muzzle.identification_log`)를 만들었다. 하지만 **테이블만으로는 아무도 모델을 쓸 수 없다.**

- 모델은 VM 파일로만 존재 → 프론트엔드가 직접 호출할 방법이 없음
- 임베딩 생성 → DB 저장 → 유사도 검색 → 임계값 판정은 여러 단계 → 매번 수동 실행 불가
- 판정 규칙(0.40, 미확정 보류)이 코드 한 곳에 모여 있어야 일관성이 유지됨

**API = 이 전 과정을 대신 처리해주는 창구.** 프론트가 사진을 보내면 결과만 돌려받는다.

### 데이터 흐름

```
[등록]
모바일 앱 → POST /muzzle/enroll (사진 여러 장 + 가축이력번호)
   → 전처리 → ONNX 추론 → 임베딩 평균 → L2 정규화
   → cattle 행 생성/확인 → muzzle.enrollment 에 저장
   → {cattle_id, enrollment_id} 반환

[식별]
카메라/앱 → POST /muzzle/identify (사진 1장)
   → 전처리 → ONNX 추론 → L2 정규화
   → pgvector 코사인 검색으로 가장 가까운 등록 임베딩 1건
   → 유사도 ≥ 0.40 이면 confirmed, 미만이면 unconfirmed(보류)
   → identification_log 에 결과 기록 (보류 건도 기록)
   → {cattle_id, similarity, decision} 반환
```

## 2. 왜 별도 서비스(포트 8001)로 분리했나

팀원 백엔드(`~/3rd_fastapi/main.py`, 포트 8000)에 라우터로 붙이는 방법도 있었으나 분리를 택했다.

| 근거          | 내용                                                                                                             |
| ------------- | ---------------------------------------------------------------------------------------------------------------- |
| 의존성 격리   | 팀원 venv에는 추론 라이브러리가 전혀 없었다. 무거운 패키지를 추가하면 버전 충돌 시 카카오 로그인까지 함께 죽는다 |
| 장애 격리     | 모델 로딩 실패가 인증·조회 API를 멈추게 하면 안 된다                                                             |
| 소유권 명확화 | 파일 단위로 파트가 분리되어 원인 추적이 쉽다                                                                     |
| 재통합 용이   | 필요해지면 `include_router` 두 줄로 합칠 수 있다                                                                 |

**팀원 코드는 한 줄도 수정하지 않았다.**

## 3. 왜 ONNX를 썼나 (`.pt` 아님)

VM `models/muzzle/weights/` 에 `muzzle_encoder.onnx` (18MB)가 이미 있었다.

|                | `.pt` (PyTorch)       | **ONNX (채택)**       |
| -------------- | --------------------- | --------------------- |
| 필요 패키지    | torch + timm (약 2GB) | onnxruntime (약 50MB) |
| 모델 구조 코드 | 필요                  | 불필요 (파일에 포함)  |
| 추론 속도      | 상대적으로 느림       | 빠름                  |
| VM 보유 여부   | 없음 (업로드 필요)    | **이미 있음**         |

`.pt`는 레시피와 재료, ONNX는 완성된 즉석식품에 해당한다. 배포에는 후자가 맞다.

### ONNX 입출력 검증 결과

```
INPUT : image      ['b', 3, 224, 224]  float32
OUTPUT: embedding  ['b', 512]          float32
```

출력 512차원 — DB `vector(512)` 컬럼과 일치 확인.
ONNX 출력은 **정규화되어 있지 않아** API 코드에서 L2 정규화를 수행한다.

## 4. 전처리를 학습 조건과 어떻게 일치시켰나

`models/muzzle/muzzle_encoder.py`(원본 PyTorch 추론 모듈)에 명시된 전처리를 그대로 ONNX판으로 이식했다.

```
BGR 디코딩 → RGB 변환
→ 그레이스케일
→ CLAHE (clipLimit=2.0, tileGridSize=8x8)
→ 3채널 복제            (ImageNet 사전학습이 3채널 요구)
→ Resize(짧은 변 255, 비율 유지)   ※ 224 × 1.14
→ CenterCrop(224)
→ /255.0
→ ImageNet 정규화 (mean=[.485,.456,.406], std=[.229,.224,.225])
→ HWC → CHW
→ ONNX 추론
→ L2 정규화
```

**이 순서가 하나라도 어긋나면 정확도가 무너진다.** 학습 설정(`run_manifest.json`)과 대조해 검증했다:

```json
{
  "GRAY": true,
  "CLAHE": true,
  "model": "efficientnet_b0",
  "img_size": 224,
  "embed_dim": 512,
  "arc_s": 30.0,
  "arc_m": 0.3
}
```

> **그레이스케일의 이유**: 데이터셋 문제 회피용 임시방편이 아니라, 모델이 코 주름 대신 **털색을 학습하는 지름길(shortcut)을 차단**하기 위한 설계다. 한우는 단색이라 특히 중요하다.

이로써 "임베딩 정규화 방식을 학습 시점과 일치시켜 고정" 항목이 해결되었다.

## 7. ★ 다른 파트가 지켜야 할 것

### 7.1 `decision`이 `unconfirmed`면 ID를 부여하지 말 것

**가장 중요한 규칙이다.**

소 A의 행동을 소 B의 이력에 기록하면 **두 개체의 baseline이 동시에 오염**되어 이후 이상 탐지 전체가 무너진다. 검출·추적에서는 재현율을 우선하지만, **개체 식별만은 반대 원칙**을 적용한다 — 놓치는 것보다 잘못 붙이는 것이 훨씬 나쁘다.

소는 하루에 급이대·음수대를 반복 방문하므로 **다음 방문에서 재확정할 기회가 반복해서 온다.** 억지로 붙일 이유가 없다.

### 7.2 DB 직접 쿼리 금지

`muzzle.enrollment`를 직접 SELECT 해서 유사도를 계산하지 말 것. 임계값 판정과 보류 로직이 API 계층에만 있으므로, 우회하면 위 원칙이 코드 레벨에서 깨진다.

### 7.3 입력은 반드시 "코 크롭" 이미지

원본 사진에서 코를 찾아 자르는 것은 **검출(YOLO) 담당 몫**이다. 이 API는 크롭을 하지 않는다. 전신·얼굴 사진을 보내면 무의미한 결과가 나온다.

### 7.4 개체 참조는 `public.cattle.id`

시계열·이벤트·조치 기록 테이블은 개체번호 문자열을 직접 들고 있지 말고 `cattle(id)`를 FK로 참조할 것. 가축이력번호는 `cattle.national_id`에 있다.

### 7.5 스키마 격리 해제에 따른 보완

2026-08-04 팀 경로 통일로 비문 테이블이 `public`으로 이동했다.
`muzzle.` 접두사가 사라져 **"내 담당이 아니다"라는 시각적 신호가 없어졌으므로**,
§7.2(직접 쿼리 금지)를 명시적 규칙으로 유지한다.

- `public.enrollment` / `public.identification_log`를 직접 SELECT하지 말 것
- `enrollment`는 일반적인 이름이므로 사용자 등록 등 다른 용도로 재사용하지 말 것
- 개체 수 집계 시 `WHERE status='active'` — 테스트 개체 제외
- uvicorn 재시작 시 `pkill -f uvicorn` 금지. 포트를 명시할 것

## 9. 검증 현황

### 9.1 완료 — 합성 데이터 배관 검증

랜덤 노이즈로 생성한 가짜 이미지로 전 과정을 확인했다.

| 단계               | 결과                                  |
| ------------------ | ------------------------------------- |
| 헬스체크           | ✅ DB 연결 정상                       |
| 개체 A 등록 (2장)  | ✅ `cattle_id: 3`                     |
| 개체 B 등록 (2장)  | ✅ `cattle_id: 4`                     |
| A 미등록 사진 조회 | ✅ A로 매칭, 유사도 0.9894, confirmed |
| B 사진 조회        | ✅ B로 매칭, 유사도 0.9890, confirmed |
| 로그 기록          | ✅                                    |

**등록 → 임베딩 저장 → 벡터 검색 → 임계값 판정 → 로그 기록의 전 경로가 작동한다.**

임베딩 직접 비교:

```
같은 개체 (A0 vs A2): 0.9755
다른 개체 (A0 vs B0): 0.9026
```

방향은 맞으나 **차이가 0.073에 불과**하고, 다른 개체조차 임계값 0.40을 크게 넘는다.
→ 합성 이미지는 학습 분포 밖(OOD) 입력이라 임베딩이 한쪽으로 몰린 것으로 판단된다. 소 코 사진이 아니므로 예상된 현상이다.

**이 테스트로 확인한 것은 "코드가 도는가"까지다. 정확도 판단 불가.**

### 9.2 완료 — 실제 이미지 정확도 검증 (2026-07-31)

Zenodo 6324361 원본으로 등록→조회 전 과정을 실행했다. 평가 개체는 노트북 셀 10의
분할 코드(`np.random.RandomState(42)` 셔플 후 앞 67두)를 재현해 **학습에 사용되지
않은 67두**로 구성했다.

**프로토콜**: 45두 등록(개체당 3장) / 미등록 22두를 함께 조회.
등록 개체 조회 220건 + 미등록 개체 조회 66건.

| 지표                | API 실측 | 노트북 | 목표   | 판정 |
| ------------------- | -------- | ------ | ------ | ---- |
| Top-1 정확도        | 0.9682   | 0.9921 | ≥ 0.90 | 충족 |
| 오배정률 @0.40      | 0.0136   | 0.0059 | ≤ 0.02 | 충족 |
| 미확정 보류율 @0.40 | 0.0182   | 0.0138 | (보조) | 유사 |

노트북 수치를 재현했다. **ONNX 변환과 `encoder_onnx.py` 전처리 이식이 학습 조건과
일치함이 확인되었다.** 노트북 대비 소폭 낮은 것은 본 테스트가 미등록 개체 22두를
함께 조회한 더 엄격한 조건이기 때문이다.

#### 운영 임계값 0.40 → 0.45 상향

노트북이 측정하지 않은 지표를 추가로 측정했다: **등록되지 않은 개체를 조회했을 때
잘못 확정하는 비율.** 실제 축사에는 미등록 개체가 상시 존재하므로 필수 지표다.

| 임계값          | 등록개체 확정률 | 미등록 오확정률 |
| --------------- | --------------- | --------------- |
| 0.30            | 1.0000          | 0.2273          |
| 0.40 (기존)     | 0.9818          | **0.0455**      |
| **0.45 (채택)** | **0.9682**      | **0.0000**      |
| 0.50            | 0.9455          | 0.0000          |
| 0.70            | 0.8273          | 0.0000          |

미등록 개체의 최고 유사도가 0.4265이므로 0.43 이상에서 전부 차단된다. 여유를 두어
**0.45를 운영값으로 채택**한다.

**근거**: 확정률 손실 1.4%p(추가 보류 3건)와 오배정 4.55% 제거의 교환이다.
보류는 다음 방문에서 회복 가능하지만 오배정은 두 개체의 baseline을 동시에 오염시켜
복구 불가능하다(기획서 §2). 명백히 유리한 교환이다.

**한계**: 본 캘리브레이션은 in-domain(Zenodo)에서만 유효하다. 교차 데이터셋에서는
오배정률이 0.1873까지 악화되므로(§10), 한우 배포 시 해당 도메인 데이터로
재보정이 필요하다.

### 13.3 크롭 — YOLO-World 실영상 실패

전 영상에서 **코 검출률 0%.** 머리 검출은 66~100%로 정상 동작했으나 코 단계가
단 한 프레임도 성공하지 못했다. §6(README)에서 보고한 교차 데이터셋 검출률
0.9925는 정면 근접 정지 사진에서 나온 값이며, 소가 움직이고 거리·각도가 변하는
실영상에는 일반화되지 않는다.

대체 방법: **브라우저 클릭으로 영상별 ROI 지정 → `cv2.matchTemplate` 다중 스케일
추적 → 매칭 점수·선명도 상위 N장 채택.** 매칭 점수 0.32 미만 프레임(코가 화면 밖)은
자동 제외된다.

평가에 수동 ROI를 쓰는 것은 타당하다. 측정 대상이 *식별 모델의 성능*이므로 검출
오차가 섞이면 원인 분리가 불가능하고, 제품의 등록 경로도 앱 가이드 오버레이로
구도를 고정한다(기획서 §5.1).

**전용 코 검출기 학습이 후속 과제 1순위임이 정량적으로 확정되었다.**

### 13.4 ★ 등록 이미지 일관성 검사 (`POST /muzzle/enroll`)

**발견한 결함:** 서로 다른 개체의 사진 여러 장을 등록하면, 임베딩 평균 후
재정규화 과정에서 **아무 개체도 아닌 벡터**가 생성되고 API가 200을 반환했다.
조용히 틀리는 유형이라 통합 시점에 식별 정확도로만 드러난다.

**대응:** 평균 직전에 쌍별 코사인 유사도의 최솟값을 검사한다.

- 임계값 `CONSISTENCY_MIN = 0.45`
- 최솟값 미만이면 **HTTP 422 `inconsistent_images`** 로 거부
- 쌍별 _최솟값_ 사용 — 평균을 쓰면 2장이 같고 1장만 달라도 통과한다
- 사진 1장이면 검사를 건너뛴다 (`consistency: null`)

응답에 `consistency` 필드가 추가되었다.

```json
{
  "cattle_id": 68,
  "national_id": "000158780357",
  "enrollment_id": 83,
  "images_used": 3,
  "consistency": 0.8712
}
```

> **주의:** 이 0.45는 §13.1에서 검토 중인 식별 임계값과 **자동 연동하지 않는다.**
> 등록 일관성은 "같은 소인가", 식별 임계값은 "누구인가"를 판정하는 것으로 목적이
> 다르다. 같은 소를 여러 각도로 찍으면 유사도가 0.7 이하로 내려갈 수 있어,
> 함께 상향하면 정상 등록이 거부될 위험이 있다.

**등록 장수 정책 확정: 최소 1장 허용 / 3장 권장.** "3장 이상"은 코드 제약이 아니라
권장사항이며(README §7-3), 1장 경로는 검사 없이 그대로 동작한다.

### 14.2 공유 VM에서의 git 작성자 설정

`azureuser` 계정을 팀 전체가 공유하므로 `git config --global`은 물론
**`--local`도 사용하면 안 된다** — 같은 클론을 여러 사람이 쓰기 때문이다.

```bash
git -c user.name="..." -c user.email="...@users.noreply.github.com" \
    commit --amend --reset-author --no-edit
git push --force-with-lease origin <branch>
```

`-c`는 해당 명령 1회에만 적용되며 설정 파일에 기록을 남기지 않는다.
검증은 `git config --get user.email`이 **아무것도 출력하지 않는 것**으로 한다.

### 15.1 임계값 코드 반영

`main.py`에 `0.45` 리터럴은 두 곳뿐이었고 **둘 다 식별 임계값이 아니었다** —
5행 주석과 20행 `CONSISTENCY_MIN`이다. 실제 값은 `encoder_onnx.py`의
`DEFAULT_THRESHOLD`를 import해 108행 `Form(DEFAULT_THRESHOLD)`로 쓰고 있었다.

**108행 한 곳만 `Form(0.70)`으로 변경했다.** `DEFAULT_THRESHOLD` 자체를 올리면
in-domain 정지 사진 경로까지 함께 올라가 정책 §4의 (A)안이 되기 때문이다.

검증: `/muzzle/openapi.json`의 `Threshold.default = 0.7`.
`/muzzle/health`는 여전히 `DEFAULT_THRESHOLD`를 보고한다(정상이나 혼동 소지 —
§11 후속 항목).

### 15.2 ★ 오프라인 평가 갤러리 ≠ 운영 DB 갤러리

§13.1의 실영상 평가는 **스크립트가 자체 생성한 등록 벡터**로 돌린 것이며,
그 개체들은 `public.enrollment`에 존재한 적이 없다. API가 조회하는 갤러리는
DB이므로 **비교 대상 자체가 없어** 전부 미확정으로 나왔다.

`crops/enroll/` 이미지를 `/muzzle/enroll`로 보내 5두 중 4두를 등록했다
(`000000000001/007/009/010`). **cow06은 HTTP 422 `inconsistent_images`로
거부되었다** — §13.4에서 추가한 등록 일관성 검사가 실데이터에서 처음 발동한
사례다.

등록 개체는 `status='demo'`로 표시했다. `active`로 두면 타 파트 집계에 섞인다.
**`demo` 상태여도 식별 갤러리에는 남으므로 조회는 정상 동작한다.**

> **8/16 통합 유의:** 각 파트의 오프라인 평가 수치는 그 파트의 DB 상태와
> 무관하게 나온다. "평가에서는 됐는데 붙이니 안 된다"의 다수가 이 문제다.

### 15.3 진단 — `threshold` 파라미터의 실효

미확정 시 1위 후보가 응답에 없어 **맞았는데 보류인지 틀렸는데 보류인지 구분할
수 없었다.** `threshold=0.30`을 요청에 실어 강제 확정시키면 1위가 드러난다.
코드 수정도 재기동도 필요 없다 — API가 `threshold`를 요청 파라미터로 받도록
설계한 근거가 여기서 확인되었다.

| 조회           | 1위            | 정답   | 유사도 범위       |
| -------------- | -------------- | ------ | ----------------- |
| cow01          | 000000000001   | ✅     | 0.648 ~ 0.739     |
| cow06 (미등록) | 000000000007   | —      | 0.536 ~ **0.717** |
| cow07          | 001 / 007 혼재 | ⚠️ 2/4 | 0.449 ~ 0.624     |
| cow10          | 000000000010   | ✅     | **0.821 ~ 0.855** |

**cow06의 0.7171** — 등록되지 않은 개체가 0.70을 넘어 남의 ID로 확정될 뻔했다.
§13.1의 "미등록 오확정 0.0667"이 실측으로 재현되었다.

cow07을 `000000000077`로 임시 등록해 측정한 `consistency`는 **0.6748**이다.
422는 아니므로 개체 혼입은 아니나 정상 등록 대비 낮다. 등록 크롭의 각도·선명도
편차가 크다는 뜻이며 조회 실패의 유력한 원인이다. 진단 개체는 즉시 삭제했다 —
같은 소의 복제본이 갤러리에 남으면 1위를 나눠 가져 결과가 오염된다.

> **`psycopg2`는 venv에 없다.** 직접 DB 조작 시 `import psycopg as pg`를 쓸 것.

### 15.4 ★ 영상 개체 확정 — 실 API 기준 오배정 0건

영상 → ROI 템플릿 추적 → 프레임 8장 크롭 → 각 프레임 /muzzle/identify → 0.70 이상만 채택 → 유사도 가중 투표 → 개체번호 1개

§13.3의 추적 로직을 재사용하되 **오프라인 비교가 아니라 라이브 API를 호출**한다.

| 영상              | 1위 | 정답 | 확정 프레임 | 최종 판정 |
| ----------------- | --- | ---- | ----------- | --------- |
| cow10_q1          | 010 | ✅   | 8/8         | **확정**  |
| cow01_q1          | 001 | ✅   | 2/8         | **확정**  |
| cow01_q2          | 007 | ❌   | 0/8         | 미확정    |
| cow07_q1          | 001 | ❌   | 0/8         | 미확정    |
| cow06_q1 (미등록) | 007 | —    | 0/8         | 미확정    |

**틀린 1위가 3건 나왔으나 단 하나도 ID를 부여하지 않았다.** 미등록 개체는
최고 유사도 0.5876으로 차단됐다. 확정률 2/5 = 0.40으로 §13.1의 0.3333과 정합한다.

**이전까지의 오배정 0.0000은 오프라인 스크립트 수치였다. 이번은 실제 API +
실제 DB 갤러리 + HTTPS 경로로 재현한 것이다.**

**다중 프레임 투표의 의미:** 단일 프레임 확정률 0.33이 8장 투표로 회복된다.

실증한 것이다.

관측된 한계 — cow01_q2 frame 96~98은 매칭 점수 0.68인데 유사도 0.20이다.
템플릿이 코가 아닌 영역으로 흘렀다(`MATCH_MIN` 상향 근거). 또한 같은 소라도
클립이 바뀌면 결과가 갈린다(cow01_q1 확정 / q2 미확정).

산출: `muzzle/video/identify_video.py`, `muzzle/results/video_api_e2e.txt`,
`~/data/muzzle_eval/results/video_api_endpoint.json`

### 15.5 ★ Caddy는 `/muzzle` 접두어를 제거하지 않는다

새 라우터가 404를 반환했고, 로그에 `"GET /muzzle/videos HTTP/1.1" 404`가 찍혔다.
**요청이 접두어를 단 채로 uvicorn에 도달한다.** 기존 경로들은 `main.py`에
접두어가 이미 박혀 있어 동작하고 있었을 뿐이다.

```python
app.include_router(video_router, prefix="/muzzle")   # 필수
SELF = "http://127.0.0.1:8001/muzzle/identify"       # 내부 자기 호출도 동일
```

내부 호출에 `127.0.0.1`을 쓰면 Caddy를 거치지 않아 빠르고 외부 네트워크 상태와
무관해진다.

신규 엔드포인트:

| 경로                                  | 기능                      |
| ------------------------------------- | ------------------------- |
| `GET /muzzle/videos`                  | ROI가 등록된 영상 목록    |
| `POST /muzzle/videos/{name}/identify` | 프레임별 판정 + 최종 확정 |

### 15.7 ★ 프론트 배포 대상이 두 개다

`worklog-20260807.md` §6.3에서 "사이트는 하나, main 머지 = 배포"로 내린 결론은
**오판이었다.** Caddyfile 확인 결과:

handle { root \* /var/www/hanwoo try_files {path} /index.html file_server }

| 사이트                                   | 정체                   | 배포 방식                                    |
| ---------------------------------------- | ---------------------- | -------------------------------------------- |
| `polite-rock-….azurestaticapps.net`      | Azure Static Web Apps  | main 머지 → **자동**                         |
| `hanwoo.koreacentral.cloudapp.azure.com` | **VM Caddy 정적 서빙** | `npm run build` → `/var/www/hanwoo` **수동** |

팀이 실사용하는 것은 VM 쪽이며 **깃 머지로는 반영되지 않는다.**

```bash
sudo cp -r /var/www/hanwoo /var/www/hanwoo.bak.$(date +%m%d)
cd ~/hanwoo-anomaly/front && npm install && npm run build
sudo rsync -a --delete dist/ /var/www/hanwoo/
```

- **빌드는 작업 트리 전체를 대상으로 한다.** 팀원의 미커밋 변경이 있으면 그대로
  배포된다. 빌드 전 `git status` 확인은 필수다.
- Caddyfile에 `handle /inference/*` → 8000 규칙이 있다. `/inference`(슬래시 없음)
  만 정적 파일로 떨어진다. 데모 시 경로에 슬래시를 붙이지 말 것.
- CORS 제한 시 **두 도메인을 모두** 목록에 넣어야 한다.

### 15.8 공유 클론 — 브랜치도 공유된다

작업 도중 `git branch --show-current`가 팀원이 만든 브랜치를 반환했다.
**같은 클론이므로 브랜치 전환이 공유된다.** 그 상태로 커밋하면 내 작업이 남의
브랜치에 들어간다.

파일 단위로도 섞인다 — `front/src/App.jsx` 한 파일에 두 사람의 변경이 공존했고,
상대가 `git add <파일>`을 하면 **내 줄이 상대 이름으로 커밋된다.**

대응 원칙:

1. **먼저 커밋하는 쪽이 자기 줄을 지킨다.** 커밋된 줄은 상대 diff에 나타나지 않는다.
2. `git add -p`로 덩어리 단위 선별. 삭제(`-`) 줄이 섞인 덩어리는 대부분 남의 작업이다.
3. **되돌릴 때 `git checkout`/`git restore`를 쓰지 말 것.** 같은 파일의 남의
   미커밋 변경까지 날아간다. 편집기에서 손으로 지우는 것이 유일하게 안전하다.

**근본 해결은 개인 클론 분리다.**

```bash
cd ~ && git clone <repo> hanwoo-yeri
cd ~/hanwoo-yeri && git config --local user.name "..." && git config --local user.email "..."
```

§14.2에서 `--local`을 금지한 것은 **공유 클론 전제**였다. 개인 클론에서는
`--local`이 안전하며, 이후 `-c` 플래그도 `git add -p`도 불필요하다.
VM 배포용 빌드만 공용 클론에서 수행한다.

## 16. 트랙-개체 바인딩 (ID 역전파) — 2026-08-11

### 16.1 문제

추적기의 `track_id` 는 임시값이다. 소가 초크포인트에 도달해 코가 보이는 순간
개체번호를 알게 되지만, 그 트랙은 이미 수 분간 관측되고 있었다. 이상행동 탐지는
개체별 시계열을 요구하므로 식별 이전 구간이 NULL 이면 baseline 을 만들 수 없다.

### 16.2 ★ 설계 — UPDATE 가 아니라 JOIN

과거 관측 행을 UPDATE 하지 않는다. 바인딩을 별도 테이블 1행으로 두고 조회 시
JOIN 한다. **INSERT 한 줄로 그 트랙의 과거 관측 전체가 개체번호를 갖는다.**

- 수천 행 UPDATE 가 없어 빠르다
- 되돌리기가 행 하나 비활성화로 끝난다
- 재판정 이력이 남는다

실측: 관측 15건 트랙에 바인딩 1회 → `affected_observations: 15`, NULL 15 → 0.

### 16.3 스키마

| 테이블 | 내용 |
|---|---|
| `public.track_segment` | 카메라·세션·track_id 단위 구간 |
| `public.track_observation` | 프레임 단위 관측 |
| `public.track_identity_binding` | 트랙 ↔ 개체 연결 |
| `public.v_identified_track_observation` | 조회 뷰 |

설계 요점 3가지.

- **`session_id`** — 추적 프로그램 재시작 시 `track_id` 가 초기화된다. 실행마다
  다른 값을 넣어 번호가 겹쳐도 다른 트랙이 되게 한다.
- **부분 유니크 인덱스** (`WHERE is_active`) — "한 트랙에 개체 2개" 충돌을 DB 가
  거부한다. 애플리케이션 조건문이 불필요하다.
- **`is_active`** — 판정 변경 시 삭제하지 않고 `false` 로 내린다.

`cattle_id` 는 `public.cattle.id` 및 `anomaly_events.cattle_id` 와 맞춰 `BIGINT`.
스키마는 `tracking` 이 아니라 `public` + `track_` 접두어로 했다 (§12 스키마 이동 이력).

### 16.4 ★ 바인딩 규칙 4가지

| # | 규칙 | 근거 |
|---|---|---|
| 1 | 유사도 0.70 미만은 **422 거부** | 잘못 붙이면 두 개체의 이력이 함께 오염된다 |

### 16.6 선택적 필터와 `IndeterminateDatatype`

`GET /tracks` 가 500 을 반환했다.

`bool | None` 파라미터가 `None` 일 때 SQL 에 그대로 넘어가 Postgres 가 타입을
결정하지 못했다. **선택적 필터를 항상 SQL 에 넣고 `NULL` 검사로 무력화하는
패턴**이 원인이다. 조건을 리스트에 모아 필요한 것만 `WHERE` 에 조립해 해결했다.
